Dampak: semua uji nyata yang dilakukan di sana tidak dapat dikaitkan ke commit yang diaudit. Tindakan: rebuild dari commit bersih dengan `scripts/build-staging-image.sh` (provenance tercatat), isi §6, jalankan G1 E2E via HTTPS. PIC: operator staging.

**G1-B02 — Tinggi (tata kelola): seluruh 24 keputusan bisnis masih Terbuka.**
Bukti: `docs/decisions.md` — D-01…D-24 berstatus Terbuka, kolom keputusan akhir kosong. Yang jatuh tempo: **D-02 dan D-03 (±1 Des 2026), D-04 (Gate 1, ±2 Des)**; D-12/D-18 diperlukan sebelum data pelanggan disimpan. Dampak: butir A6 tidak dapat lulus; asumsi menumpuk di kode (10 menit kelayakan otomatisasi, retensi 30 hari, dll.). Tindakan: satu sesi keputusan (§6 Fase 0). PIC: pemilik.

**G1-B03 — Sedang: backup di server hanya "dinyatakan".**
Bukti: `daftar-tindakan-pemilik.md` G7 dan laporan tindak lanjut §5: checksum cocok dan restore terisolasi dinyatakan pemilik, "diverifikasi auditor" tanpa nama/tanggal/catatan; jadwal, salinan di luar VPS, PIC pembuat/pemeriksa belum ada. Drill lokal/CI lulus (TERBUKTI simulasi). Tindakan: catat artefak teks (nama berkas, SHA-256, ukuran, lokasi salinan, durasi restore, hitungan baris) — tanpa tangkapan layar. PIC: pemilik/operator.

**G1-B04 — Sedang: guard nomor operasional berjalan tanpa daftar hash di CI.**
Bukti: log job `139560647363` run #27: `OPERATIONAL_NUMBER_HASHES:` kosong → aturan G4 di `scripts/guard-operational.mjs` tidak pernah aktif; yang berjalan hanya pencocokan akhiran `1119`/`0124`. Guard juga tidak memeriksa `phone_number_id`/WABA ID Meta milik Admisi/Hotline. Tindakan: pemilik mengisi secret repository `OPERATIONAL_NUMBER_HASHES` (sha256 digit E.164 Admisi + Hotline + Kemitraan); developer menambah aturan untuk ID Meta operasional (juga lewat secret hash). PIC: pemilik (secret) + developer.

**G1-B05 — Sedang (tata kelola): alur PR dan proteksi branch yang diwajibkan AGENTS.md §2 dan §10.1 tidak dijalankan.**
Bukti: remote hanya punya satu branch `claude/lucid-carson-blf4x0`; tidak ada `main`, tidak ada branch `tahap-N-*`, tidak ada PR, tidak ada tag. Tahap 1–3 di-push langsung. Akibatnya "merge diblokir jika CI gagal" tidak pernah ditegakkan — CI hanya informatif. Tindakan: buat `main` dari commit yang diterima, aktifkan branch protection (wajib 4 job CI hijau + 1 persetujuan pemilik), dan mulai Tahap 4 di `tahap-4-*` lewat PR. PIC: pemilik (pengaturan GitHub) + developer.

### Gate 2

**G2-B01 — Tinggi: CCP 2.8, 2.9, 2.10 belum dapat lulus nyata; 2.9 tidak dapat diamati dengan kode sekarang.**
Bukti: placeholder `G2 (NYATA)` masih dilewati; M-11 (echo) belum dijalankan; S-12 (`verifikasi-dokumentasi-meta-2026-11-26.md`) — history hanya dikirim Meta setelah aplikasi **meminta sinkronisasi** (SMB App Data API, sekali, ≤ 24 jam sejak onboarding); TE One tidak memiliki pemicu itu. Tindakan: (a) developer membangun pemicu sinkronisasi history/kontak di `whatsapp-adapter` di balik flag mati + test; (b) uji pada **nomor uji bersih** yang di-onboard baru, dengan `history` dan `smb_message_echoes` di-subscribe sebelum onboarding. PIC: developer + pemilik.

**G2-B02 — Tinggi (privasi/PDP): pesan pelanggan nyata mengalir ke staging.**
Bukti: laporan Fase 0 — ponsel …6319 berisi chat pelanggan nyata; field `messages` aktif ke webhook staging sejak ±16.00 WIB 25 Nov; D-18 belum diputuskan; isolasi staging belum terbukti (G1-B01). Kode mengarantina pengirim di luar daftar uji dan **membuang payload** setelah diproses (`ingest.ts:101–103`, `worker.ts:25`) — mitigasi yang benar — tetapi payload mentah (nomor + isi pesan) tersimpan dulu di `inbound_events` sampai diproses, dan lihat G2-B03 untuk kondisi saat event tidak segera diproses. AGENTS.md §3.5 melarang data pelanggan asli di bukti uji; staging tanpa keputusan retensi menambah risiko. Tindakan: putuskan apakah …6319 tetap terhubung ke staging (formulir A-2c / G12); bila tetap, hitung (angka saja) event karantina dan event `pending` lama secara berkala sampai nomor uji bersih tersedia. PIC: pemilik.

**G2-B03 — Sedang (analisis kode): pada mode inline-saja, event dapat tertahan `pending` dengan payload utuh, dan perbaikan G2-A06 tidak aktif.**
Bukti: `worker.ts:46–58` — `kickProcessing()` keluar bila `kicking=true`, dan loop berhenti setelah satu klaim kosong atau 10 batch (maks. 200 event). Event yang tersimpan tepat setelah klaim kosong terakhir tetapi sebelum `kicking=false`, atau event ke-201 dalam satu lonjakan, tidak diproses sampai webhook berikutnya. Staging berjalan tanpa worker (S-10), sehingga `purgeRawPayloads`, `expireStaleProcessing` (perbaikan G2-A06) dan rekonsiliasi **tidak pernah berjalan**; `purgeRawPayloads` juga tidak menyentuh status `pending`. Belum direproduksi. Tindakan: jalankan worker di staging (keputusan A-4) — ini menutup S-10 dan sebagian besar G2-B03; tambahkan perulangan "kick ulang bila ada event baru selama kick" + test. PIC: developer + pemilik (A-4).

**G2-B04 — Rendah-sedang: echo tanpa nomor penerima tidak tercatat (S-11, dikonfirmasi).**
Bukti: `grep to_user_id src/` kosong. Echo ke kontak yang hanya punya BSUID/username dikarantina `echo_tanpa_penerima`. Aman, tetapi bertentangan dengan AGENTS.md §7 ("echo dicatat sebagai pesan keluar"). Tindakan: dukung `to_user_id` + test. PIC: developer.

**G2-B05 — Sedang: hasil uji nyata 25 Nov tidak dapat diperiksa pihak lain.**
Bukti: `pernyataan-pemilik-uji-staging-2026-11-25.md` — butir 1–8 dinyatakan pemilik, tanpa artefak (keputusan pemilik), terikat ke checkout `9c297d3`, bukan ke image yang berjalan. Ini bukan tuduhan bahwa hasilnya salah. Jalan tercepat tanpa tangkapan layar: **J2** (keluaran teks: `meta:check`, hitungan kueri, `docker image inspect`) atau **J1** (auditor memeriksa baris DB staging secara baca-saja). PIC: pemilik.
